# P115、P123、P140 思考题解答（L2 part2）

> 作业依据：L2 part2 第 115 张（参数、计算量与实际速度）、第 123 张（Review：优化设置也是比较条件）、第 140 张（训练预算中的长上下文修正）。三题原题引自幻灯片原文（下引）。
> 运行环境：WSL2 Ubuntu + NVIDIA RTX 3050 Laptop 4GB，torch 2.15.0+cu132。**所有数字来自真实运行**（脚本与结果见 `scripts/`、`results/`，可复现）。

## 摘要

三题共用一条主线：**课件账本公式（24Lsd²、4Ls²d、6ND、12LDsd）算的是"数学账"，实际速度与最终损失由"工程账"决定**。

- **P115**（计算量 vs 速度）：实测微基准证明"FLOPs 减少 ≠ 运行变快"的两个来源——(1) 数学掩码不等于执行跳算（causal 掩码把配对"减半"，墙钟反而慢 8–33%，因为执行时仍算了完整方阵、还多了掩码开销）；(2) 即使真的减少了执行量（GQA 把 K/V 投影缩小 7–12%、注意力 s² 主项不变），速度仍几乎不变，因为省下的不是瓶颈处的量。而同一因果数学量换用真正跳过未来配对的 flash 内核，**快 19–22 倍**——实现才是决定项。答案本体是一份按顺序执行的**测量清单**（profiler 分解、有效 TFLOPS vs 实测峰值、roofline、利用率、内核后端、形状与批量、数据传输），每一步都对应一个真实数字，并如实记录了两次测量异常（瞬时带宽抖动、批量尖峰伪瓶颈）与复查结果。
- **P123**（训练配方）：固定 1,048,576 个训练窗口（每窗 64 token，共 67.1M token = 相同 6ND 主项 FLOPs）扫 9 种配方，最终验证困惑度从 88.29 到 238.85，相差 2.7 倍；单是学习率一项（3e-4→3e-2）就造成全部差异的主体。证明"同样 FLOPs"只约束运算总量，不约束优化轨迹。
- **P140**（System One 决策模型）：先复核课件算例（s=4096 修正 1/6、s=32768 修正 4/3，与幻灯片一致），再按 "jev" 类模型的公开特征（TypeSafe Jev、开源对照 StartLux-Decision：MoE 35B-A3B、flash-linear-attention、双向注意力、单次前向多问题并行、RLCD）把公式逐项改写，并给出手算账本（`results/flops_ledger.txt`）。

## 题目原文

**P115**：关于 Transformer 模型的参数量与计算量。理解架构要知道各模块"做什么"并逐步骤说明保存多少参数、执行多少运算、产生多少中间状态、搬运多少数据。……逐项核算是起点，结合运行条件定位瓶颈，才能提出有效改进。同一架构在训练、输入预填充与逐 token 生成时，瓶颈可能不同。减少参数、减少 FLOPs、减少显存和降低延迟，需要分别验证。**思考题：如果一种改进减少了计算量，运行却没有变快，下一步应该测量什么？**

**P123**：Review：优化设置也是比较条件。学习率、衰减日程、批量、数值精度和检查点选择都可能改变相同预算下的最终损失。某模型训练不足可能来自 token 量不够，也可能来自不适合其训练时长的优化模式。比较结构时应尽量控制这些设置；无法控制时只能先比较完整训练方案。**学习较好的同学问自己：同样 FLOPs 时，训练配方的影响有多大？刚入门的同学问自己：深度学习的所谓配方都包括哪些？Transformer 论文提到了哪些？**（幻灯片还附了一个继续追问：如果批量翻倍、更新次数减半，总 token 数和主要 FLOPs 近似不变，结果是否一定相同？）

**P140**：训练预算中的长上下文修正。简化及近似：F_train ≈ 6N_block·D + 12LDsd。……固定累计 D，注意力修正仍随序列长度 s 线性增加；仅用 6ND 会遗漏这一项。d=4096 时，s=4096 的修正约为参数项的 1/6；s=32,768 时约为 4/3。若因果内核跳过未来位置，配对项约减半；重计算、词表头和通信仍需单独核算。**建议分享在 Piazza 上的思考题：对于当前大热的 "jev" 类 System One 决策模型，上面的公式需要做哪些修改？当然，决策模型的架构 jev 没有放出论文，但是类似的开源模型可太多了，建议搜集并学习。**

## 一、P115：减少计算量的改进没有变快，下一步测量什么

### 1.1 实验设计：把"计算量减少"拆成两种情况

"计算量减少"至少有两种实现方式，速度表现完全不同：

- **A 类：数学上减少、执行上没减少**。因果掩码把注意力配对数"数学减半"（2LBs²d → LBs²d），但掩码实现只是给未来位置加 −inf，`q @ k^T` 的完整 s² 方阵照样执行，还额外多了掩码构造与覆盖的成本。这是课件反复强调的"数学掩码 ≠ 执行跳算"。
- **B 类：执行量真实减少**。GQA（KV 头 8→2）把 K/V 投影真实缩小，但按课件 GQA 页的口径，s² 配对乘加由 query 总宽度决定、**不变**——省下的不是注意力主项。

实验（全部真实运行于 RTX 3050 Laptop，`scripts/micro_bench.py` → `results/micro_bench.json`）：L=6、d=512、h=8 的微型 GPT 块栈（手写注意力，FLOPs 可按课件公式精确核算），固定 B·s=4096 的 5 个形状 × 3 种实现（MHA_full / MHA_causal / GQA4_full）；另加一组"同一因果数学量、三种内核"的 SDPA 对照（math 只掩码 / efficient / flash 真跳过）。

### 1.2 直接答案：一份按顺序执行的测量清单

**第 1 步：先做时间分解（profiler），确认"没变快"发生在哪个环节。** 我的测量：单次前向迭代发射 **834 个算子**；CPU 发射耗时 59.0ms 对 CUDA 执行 85.0ms（s=128）与 136.1ms 对 182.5ms（s=2048）——CPU 始终跑在 GPU 前面，本环境发射不是瓶颈；CPU 侧耗时大头是 aten::mm/copy_/triu。注意 causal 变体的 triu 布尔掩码**每次迭代都在设备上重建一张 S×S 掩码**并整体覆盖分数矩阵——"数学掩码"本身有隐性成本（s=2048 时 6 层共 25MB/迭代的额外写入）。

**第 2 步：测实际达到的 TFLOPS，而不是相信名义 FLOPs。** A 类改进：s=2048 时数学 FLOPs 从 257.7G"减半"到 206.2G，但执行 FLOPs 仍是 257.7G，墙钟 220.6ms 对完整方阵 166.1ms——**反而慢 33%**（s=128 时慢 8%）。B 类改进：GQA4 执行 FLOPs 真的少了 7–12%（如 s=128：141.7G 对 161.1G），墙钟 56.7ms 对 61.5ms 只快 8%，s=2048 时 183.7ms 对 166.1ms 反而慢 11%——省下的投影项不是瓶颈，且 einsum 分组路径有自身开销。执行口径的有效 TFLOPS 全程只有 1.17–2.62。

**第 3 步：测算术强度，对照 roofline。** 本机实测（同一脚本、同一次运行）：GEMM 峰值 fp32 **3.24** TFLOPS、fp16 **9.24** TFLOPS；显存带宽 **183 GB/s**（copy 64/256/512MB 与 add 流式探针互相一致）→ ridge point ≈ **17.7 FLOP/byte**。本实验各形状的算术强度都高于 ridge，名义上"算力受限"，但有效 TFLOPS 只到峰值的 36–81%——差距来自注意力栈本身的实现效率（K=64 的小维 bmm、softmax、逐元素掩码），roofline 判定不了"内核写得好不好"。

**第 4 步：测 GPU 利用率与功耗（是不是空转）。** nvidia-smi 采样：小形状 90.3%、大形状 97.8% 利用率，功耗 43–46W。利用率接近 100%，有效 TFLOPS 却只有 0.7–2.9——**利用率 ≠ 效率**：GPU 满负荷运转，但干的不全是 FMA。

**第 5 步：测内核后端——同一数学量，实现差 20 倍。** 同一因果注意力、同一张卡（fp16）：math 后端只掩码不跳过，s=2048 时 24.06ms；flash 后端真正跳过未来配对，**1.09ms，快 22 倍**（s=512 时 19 倍、s=1024 时 21 倍；efficient 后端 1.26ms 也跳过）。这就是"改进必须打在瓶颈处"的正反例闭环：掩码减的是数学、跳过减的才是执行。

**第 6 步：测形状与批量（prefill vs decode 的雏形）。** 固定 s=400 扫 batch：B=1–16 每 token 28.5–34.4µs，几乎不随 batch 变（与第 1 步 CPU 不落后互相印证）。B=32 首测 114.8µs/token 的异常尖峰在连续两次运行中复现（1357/1469ms），但**新进程重测 3 次为 314–400ms（28.8µs/token），恢复正常**——形状循环后长寿命模型实例的分配器/工作区状态造成伪瓶颈。教训：单次测量会撒谎，"改进前 vs 改进后"必须同进程状态对照、异常点必须复查。

**第 7 步：测数据传输与显存。** copy 512MB 首测只得 6.2 GB/s（异常），复测 183.2 GB/s 且三个尺寸与 add 探针一致——首测是瞬时环境干扰（本机 WSL2 与 Windows 桌面共享同一块 GPU）。显存带宽这类"硬上限"也必须复测确认，否则会把环境抖动当成硬件属性。

**结论性命题**（全部由上面测量支持）："计算量减少"只有在减少的是**当前瓶颈处的执行量**时才加速。A 类改进（因果掩码）执行量根本没减少、还多了掩码开销，所以更慢；B 类改进（GQA）省的是投影而非 s² 主项，所以几乎不加速；而真正跳过未来配对的 flash 内核快了 20 倍。所以下一步该测的是：**先分解时间，再对照实测 roofline 找瓶颈，最后确认改进是否打在瓶颈上**——并且每一步都要在相同环境状态下复测。

## 二、P123：同样 FLOPs 时，训练配方的影响有多大

### 2.1 入门问：深度学习"配方"包括哪些，Transformer 论文提到了哪些

配方（recipe）= 数据与预处理、训练目标、批量与训练长度（步数）、优化器、学习率日程（warmup + 衰减）、正则化（dropout、weight decay、标签平滑）、初始化与数值设置、检查点选择。

Transformer 论文（Vaswani et al., 2017）的配方：数据 WMT2014 En-De/Fr，BPE/wordpiece 子词切分（论文口径约 37k 合并操作）；按相近长度组织句对，每批约 25k 源端 token + 25k 目标端 token；优化器 Adam β₁=0.9、β₂=0.98、ε=1e-9；前 4000 步线性预热后按步数平方根倒数衰减；dropout 0.1（基础模型）与标签平滑 0.1；基础模型训练 10 万步、大模型 30 万步。

### 2.2 进阶问：同样 FLOPs 时，配方影响有多大——固定预算实测

**关键实验设计**：总 FLOPs ≈ 6ND（N、D 固定时只由总 token 决定），所以"同样 FLOPs"= "同样总 token 预算"。我固定总训练窗口 B × steps = 1,048,576（每窗 64 token，总 token = 67,108,864，对同一模型即相同 6ND 主项 FLOPs），在人民日报 1998 语料（hw3/4_4 数据）上训练字符级 MiniGPT（d=64、L=2、h=4、词表 4566），9 种配方只改一项设置，最终验证困惑度对比。工程上有一个如实记录的绕行：B=1024 时词表头 logits（1024×64×4566×fp32 ≈ 1.2GB）超出 4GB 显存（WSL2 与 Windows 桌面共享同一块卡），改为按位置分块计算词表头损失（head 逐位置独立，分块与整块数学等价、仅求和顺序不同，`head_loss` chunk=8）+ 训练时块级梯度重计算（`torch.utils.checkpoint`，重算前向逐位一致），**全部 9 种配方共用同一条代码路径**；首次运行在 R3 后被外部中断，最终结果来自同代码的一次完整重跑（中断的 R1–R3 留档于 `results/recipe_results_interrupted_r1r3.json`，重跑日志 `results/recipe_exp.log`）：

| 配方（除标注外均同基线） | 改动 | 最终验证困惑度 | 训练损失 | 墙钟 |
|---|---|---|---|---|
| R1 基线 | B=512, steps=2048, lr=3e-3, cosine, warmup=102, dropout=0.1 | 115.23 | 4.53 | 265s |
| R2 lr 小 10 倍 | lr=3e-4 | 238.85 | 5.44 | 269s |
| R3 lr 大 10 倍 | lr=3e-2 | **88.29** | 4.00 | 280s |
| R4 批量翻倍 | B=1024, steps=1024（同 lr） | 130.45 | 4.69 | 285s |
| R5 批量翻倍+lr√2 | B=1024, steps=1024, lr=3e-3·√2 | 117.80 | 4.56 | 288s |
| R6 无 dropout | dropout=0 | 114.38 | 4.41 | 279s |
| R7 标签平滑 0.1 | label_smoothing=0.1 | 115.68 | 5.19 | 330s |
| R8 常数 lr | schedule=constant | 101.55 | 4.35 | 277s |
| R9 长 warmup | warmup=1024（=步数 50%） | 114.84 | 4.53 | 280s |

（全部配方：相同模型、相同总 token = 67,108,864、相同 6ND 主项 FLOPs；无任何配方发散。完整轨迹与曲线见 `figs/p123_recipes.png`。）

**结论**：同样 6ND FLOPs 下，最终验证困惑度从 **88.29**（R3）到 **238.85**（R2），相差 **2.7 倍**。差异主体来自学习率一项：lr 从 3e-4 提到 3e-2（100 倍跨度）把困惑度打掉 63%（238.85→88.29），而 lr=3e-2 在本预算下并未发散——它比基线的 3e-3 还低 23%。批量翻倍（同 lr）劣化 13%，lr√2 线性缩放只补偿约一半（R5 117.80 仍比 R1 差 2.2%）；常数 lr 反而比 cosine 低 12%（2000 步量级的短预算里 cosine 衰减过早）；dropout、标签平滑、warmup 长度的改动都在 ±1% 以内。这正是 P123"优化设置也是比较条件"的量化版：预算相同，配方决定最终损失。

### 2.3 继续追问：批量翻倍、更新次数减半，结果一定相同吗

**不一定。** 总 token 与 6ND 主项 FLOPs 近似不变，但改变的恰恰是"配方"里最敏感的两项：

1. **噪声与泛化**：大批量每步梯度估计方差小、等效噪声小，小批量隐式正则更强；在固定预算下这与优化轨迹直接相关（我的 R4 vs R1 实测：130.45 对 115.23，批量翻倍、步数减半后同 lr 下劣化 13.2%）。
2. **更新次数减半 = 学习率日程失配**：warmup 比例、cosine 终点、以及"每个 token 被更新的次数"（部分 token 从被更新 2 次变为 1 次）都变了。线性缩放法则 lr∝√B 只是补偿一阶近似（我的 R5 vs R4：lr√2 后 117.80 对 130.45，改善 9.7%，但离 R1 的 115.23 还差 2.2%——只补偿了约一半）。
3. 优化器状态、梯度剪裁、EMA 等都与步数耦合，不是 token 数不变就能不变的。

所以"批量翻倍、步数减半"只是保证**运算账**相同，不保证**优化轨迹**相同——这正是 P123"优化设置也是比较条件"的本意：比较架构时若无法控制配方，就只能比较完整训练方案。

### 3.1 先复现课件公式（复核通过）

课件公式 F_train ≈ 6N_block·D + 12LDsd，其中 N_block = 12Ld²（经典普通 FFN），第二项为完整方阵注意力前向的约 3 倍。我用手算账本复核（`scripts/flops_ledger.py`，输出 `results/flops_ledger.txt`）：取 L=32、d=4096、D=1e12 token，s=4096 时注意力项/参数项 = 0.1667（= 1/6），s=32768 时 = 1.3333（= 4/3），与幻灯片完全一致；比值解析式为 s/(6d)。

这个公式有三条隐含假设，System One 决策模型把它们逐一打破：(a) 稠密 FFN、每个 token 触碰全部参数；(b) MHA + 完整方阵配对（12LDsd 里的 12 = 4LBs²d × 3）；(c) 只覆盖预训练前反向主项，不含 RL 采样、词表头与部署侧成本。

### 3.2 "jev" 类模型是什么（调研结论，公开口径）

- **Jev（TypeSafe AI，2026-09-15 发布）**：首个 System One 决策模型（ChatGPT 共同发明人 Diogo Almeida 主导）。不做文本生成：输入一份程序状态 + 预定义问题，直接返回**带校准概率的类型化决策**——三种原语 Choice（候选选择）/ Score（有序评分）/ Noul（命题成立概率）。训练方法是面向校准决策的强化学习 RLCD（让输出概率与真实频率匹配）。公开性能口径：延迟 70–500 ms，成本约 $0.042/百万输入 token、输出免费，速度最高提升上百倍。**架构论文未公开**（幻灯片明说），因此下面所有结构推断都基于同类开源模型。
- **StartLux-Decision（上海 StartLux Labs，开源，HF 决策榜第一）**：同类架构的公开对照，`startlux-models/StartLux-Decision-4B` 可下载，技术口径公开：**MoE（35B-A3B，每 token 仅激活约 3B 参数，grouped matmul + CUDA Graphs）**；**flash-linear-attention 线性注意力 + causal-conv1d 内核**（短请求延迟极低）；**Instant 双向注意力**；**单次前向多问题并行**（选项渲染为字母 token，从字母位置直接读出概率）；256K 长状态按块读取一次、每个问题从表示分支读出；BF16/Q8_0 量化下 99–100% 决策结果与原权重一致；自研 RLCD² 与 AutoThink（置信度引导的自适应"思考预算"）。
- 其他开源对照：Chinese-Jev（面向中文的紧凑 System One 模型）、xuhaodev 的足球领域决策模型等。

### 3.3 逐项修改（推导见账本，这里给结论）

| 课件公式的成分 | System One 决策模型的修改 | 依据 |
|---|---|---|
| 6N_block·D，N_block=12Ld²（稠密） | 改用**激活参数**：N_active = L·(12d² + 2k·d·d_ff)，k 为每 token 激活专家数。35B-A3B 口径下参数主项降为稠密同参模型的 3/35 ≈ 1/11.7 | StartLux MoE 公开口径 |
| 12LDsd 的 s²（完整方阵） | **线性注意力直接消掉 s²**：每 token 每层两次 d·m 小乘加（状态更新 k·vᵀ 与输出 q·S），前反向合计 12·L·D·d·m，**与 s 无关**——m=d 时等价于把方阵项固定在 s=d 的值；只有 s>m 时才更省（方向性）。同时"分数矩阵"显存从 L·B·h·s²·b 变为状态量 L·B·h·d·m·b（s=8192、h=24 时从 3.2GB/层变为 m=64 时 4.7MB） | flash-linear-attention 的计算结构 |
| 12LDsd 的配对项 × GQA | **不变**：多组查询共享 KV 头，但各查询的分数与加权仍各算一套，s² 配对乘加由 query 总宽度决定（课件 GQA 页明文："KV 头数减少到 1/4，不等于整个注意力计算减少到 1/4"） | 课件 GQA 页推导 |
| 6N_block·D 的 K/V 投影部分 | N_block：12d² → 12d² − 2d²(1 − n_kv/h)，n_kv/h=1/8 时约 10.25d²（参数与投影 FLOPs 同步缩小）；KV 缓存 2LBs·n_kv·hd·b 为 MHA 的 1/8（存储账，不进 FLOPs 公式） | GQA 定义 + 课件 KV 缓存算例 |
| 因果减半 | 双向注意力不减半；换取的是**同一 state 上 K 个问题并行作答**，每问题成本 = 全量项/K（公式之外的摊销，需单独记账） | StartLux Instant 双向注意力 |
| 词表头（课件注明"仍需单独核算"） | 输出不是下一个 token：词表头 V·d（V~10 万）消失，换成 choice/score/noul 有界头，每 token 输出 2·d·(c+1) 量级（c 为候选数，个位数），小 4 个数量级 | Jev 三原语 + StartLux 字母位置读出 |
| 6ND 只覆盖预训练 | 加上 **RLCD 在线采样项**：每步更新 (2G+6)·N_active·s（G 次前向采样 + 1 次前反向训练）。关键：决策模型的"采样输出"是几个标量/概率，**没有思维链**，s 里没有数千 token 的 t_think | Jev/StartLux 的 RLCD 训练 |

**修改后的账本**：

```
F_train ≈ 6·N_active·D
        + 12·L·D·d·m                 （线性注意力，m 状态扩展维；方阵注意力则为 12·L·D·s·d，
                                      GQA 不改变配对项，只把 K/V 投影缩进 N_active）
        + 输出头小项 2·d·(c+1)·K      （可忽略，但需列明）
        + Q·U·(2G+6)·N_active·s       （RLCD 在线采样，若训练含 RL）
```

6ND 的"ND 主项结构"不变，变的是每一项的系数与变量。

### 3.4 手算账本数字（示意配置，数字自洽；非未公开论文的真实逐层参数）

- **算例 S1**（L=16, d=3072, E=16 专家 k=2 激活, n_kv/h=1/8, D=0.5T token）：N_total≈6.4B、N_active≈2.15B（激活比 0.34，K/V 投影已按 GQA 缩小）。方阵配对项占参数项的比例随 s 上升：s=2048 → 0.094，s=8192 → 0.374，s=32768 → 1.497；线性注意力固定为 0.140（m=d 口径）且与 s 无关——注意 s=2048 < d 时线性反而更贵，**长状态决策场景（256K 分块）下这才是结构性的差别**。
- **算例 S2**（RLCD：G=8 路采样、每状态 4 次更新、100 万状态、典型状态 s=512）：F_RLCD ≈ 9.69e19，只占 S1 预训练主项的 **1.5%**——单次前向让在线 RL 可负担。同一公式把 s 换成 s+t_think：带 2000 token 思维链的 System Two 放大 (s+t)/s = 4.9 倍（s=128、t=8000 时 63.5 倍）。**这就是"决策模型才敢把 RL 当主训练手段"的成本根源。** AutoThink 式自适应推理则把"额外前向次数"变成随机变量，公式再乘 (1+E[额外前向])。
- **算例 S3**（部署侧）：7B LLM 每 query ≈ 2N(s_in+s_out) = 3.57e13 FLOPs；S1 决策模型每问题 ≈ 2·N_active·s_in/K（K=10 摊薄）≈ 1.76e12，约为 LLM 的 1/20——与 Jev"输出免费、输入计价"的公开价格结构同向。

### 3.5 公式之外：什么没变、什么仍需单独核算

1. 软 max（softmax）、激活重计算、通信、路由网络本身（MoE 的 all-to-all）仍不在公式里——原课件的提醒原样成立。GQA 的 KV 缓存（2LBs·n_kv·hd·b）是存储账，也要单独列。
2. 数值精度不改变 FLOPs，只改变墙钟时间：StartLux 的量化鲁棒性（Q8_0 与原权重决策一致）说明这一项对部署账本很重要，但对 FLOPs 账本无影响。
3. 诚实声明：Jev 无公开论文，StartLux 公开的是家族口径（35B-A3B、线性注意力、双向、RLCD²）而非逐层配置；上面所有具体数字都是**自洽的示意算例**，用于演示"每一项怎么改、数量级如何"，不是对任何真实模型训练日志的复算。

## 结论与局限

- **P115**：速度由"执行口径 × 实现效率 × 瓶颈位置"三者决定，数学 FLOPs 只给下限。实测闭环：因果掩码减数学不减执行、反而慢 8–33%；GQA 省投影不省 s² 主项、墙钟 ±10% 无收益；flash 真跳过未来配对、快 19–22 倍。因此"改进没变快"时的下一步是一份按顺序的测量清单：profiler 分解 → 有效 TFLOPS → 实测 roofline → 利用率 vs 效率 → 内核后端 → 形状/批量 → 数据搬运，且每一步同环境复测。
- **P123**：同样 6ND FLOPs（= 同总 token）下，9 种配方的最终验证困惑度相差 2.7 倍（88.29–238.85），学习率是差异主体，批量×日程的交互次之，dropout/标签平滑/warmup 在 ±1%。批量翻倍+步数减半（同 lr）劣化 13.2%，lr√2 只补偿约一半——"运算账"相同不保证"优化账"相同。
- **P140**：System One 决策模型把 6ND 的三条隐含假设（稠密参数、完整方阵配对、纯预训练）逐一打破：参数项改用激活参数 N_active（35B-A3B 下约 1/12），s² 项被线性注意力消掉成 12·L·D·d·m，词表头换成有界输出头，再加 RLCD 采样项；GQA 不改变配对项。6ND 的 ND 主项结构不变，变的是每一项的系数与变量——且无思维链的 s 才是"RL 当主训练手段"的成本前提（S2 仅占预训练 1.5%，带 CoT 则放大 4.9–63.5 倍）。
- **共同结论**：课件的账本公式是"数学账"，速度是"工程账"，损失是"优化账"——三者各自有独立的核对方法，改进只有打在**当前瓶颈处**才兑现成墙钟时间或更低的损失。
- **局限**：4GB 笔记本卡 + WSL2 的测量值带有本机特征（实测 GEMM 峰值仅为规格值的约 37%，且与 Windows 桌面共享显存，B=1024 时需分块词表头 + 梯度重计算才能放进显存——绕行本身已成实验记录的一部分）；P123 是 67.1M token 预算下的微型字符模型，结论是方法学演示而非规模外推；P140 的 jev 无公开论文，所有架构数字是标注清楚的示意算例。所有数字来自真实运行，脚本与结果文件全部入库可复现。
