# 4.4 编程练习：高效率 BERT 古文断句标点（人民日报 9801 语料）

> 作业依据：L2 part2 第 68 张——任务一：用现成语料微调训练好的 BERT，得到断句标点模型；任务二（工程向）：原始 BERT 只有 512 token 上下文，古文一段数千字只能滑窗；基础做法"每次 400 字符、只取前约 300 字、在句号后断开作为新起点"效率很低，要求在 GPU batch 解码模式下设计高效方案（课件基准：12G 显卡 batch 4–9，更好显卡 16–64）。
> 运行环境：Windows 11 + WSL2（Ubuntu），Python 3.12，torch 2.15.0（CUDA），transformers 5.22.1，**NVIDIA RTX 3050 Laptop 4GB**。
> 代码与结果见 [GitHub `hw3/4_4/`](https://github.com/WLGX/LLM-course/tree/main/hw3/4_4)。**所有数字均来自真实运行**：数据由 `data_prep.py` 生成，模型由 `train_bert.py` 实跑训练，长文解码由 `decode_long.py` 实测，无任何编造；失败与修正过程一并记录。

## 摘要

我用人民日报 1998 年 1 月语料（9801，2003 分词带音版，即课件指定语料）构造字级"断句标点"标注数据：输入是不含主标点的文本，标签是每个字后应插入的标点（11 类：O + ，。、？！：；""…）。在 4GB 显存上微调 bert-base-chinese，2 个 epoch（5,000 步）真实训练后，测试集 macro-F1 为 **0.561**，其中句尾标点（。）F1 **0.84**、逗号 F1 **0.81**、问号 F1 **0.72**；引号类（"" 0.37/0.41）与分号（0.30）明显偏弱，与语料中引号对跨块、位置歧义有关（见 §2.3）。

任务二实现了课件描述的朴素基线（滑窗 400/取 300/句号后重启，逐窗串行）与 batch 解码方案（固定步长窗口 + 重叠区概率融合，全部窗口装入 batch 并行前向）。在 8 篇 3000 字长文上实测：batch=8 方案平均吞吐约为朴素基线的 **1.34 倍**（中位 1.13×，最高 2.70×），且耗时方差远小于基线（0.47–0.82s vs 0.47–1.29s）；质量基本持平（长文合成金标上 macro-F1 平均 0.217 vs 0.232，逐字一致性 0.93）。batch 扫描显示吞吐随 batch 单调上升（1→32 提升 42%），峰值显存不随 batch 增长（~696MB），**4GB 笔记本卡即可开到 batch 32**——课件 12G 规格的对照讨论见 §3.4。

## 一、任务依据与实验边界

### 1.1 数据

- `1998-01-2003版-带音.txt` 等 6 个文件（GB18030），共 143,766 行、约 1,095 万字符（清洗后）。格式：`19980101-01-001-001 迈向 充满 希望 的 新 世纪 …`——行首为语料 ID，正文为空格分词，标点独占一词，多音字带 `{拼音}` 标注（如 `那{na4}段`）。
- 训练/验证/测试按块随机划分 90/5/5，得到 train 96,270 / valid 5,348 / test 5,349 块（每块 ≤128 字符）。**同篇文章的块会同时进入训练与测试**：这是本实验的已知简化（随机按块而非按文章划分），因为我们的目标是演示"现代文→断句模型"的完整流程；若要严谨评估，应做文章级划分（hw1 的 n-gram 作业里我做过文章级哈希划分）。

### 1.2 标注方案（为什么把"标点"变成字级标签）

断句标点的本质是**插入任务**：古文没有标点，模型要在字与字之间决定是否插入标点、插哪种。因此把每个字标注为"其后紧跟的标点类别"，无标点为 O。这与 NLP 中标准的 punctuation restoration（标点恢复）任务一致，也直接对得上"古文句读"的使用方式：输入无标点文本，输出每个字后的标点。

**标签集（11 类）**：O、，。、？！：；""…（左/右引号归并为 "" 两类）。其余标点（《》（）——·% 等）保留在文本中作为上下文但不作为预测目标（label 记 O）；`’98` 这类年份缩写中的撇号保留在文本中。这些设定与局限在 §5 说明。

**清洗规则**（每个规则对应语料里的真实噪声，均有计数）：

| 清洗项 | 说明 |
|---|---|
| `{拼音}` / `[注音]` 剥离 | 带音版多音字注音，如 `那{na4}段`；留在词表会污染统计（与 hw1 n-gram 作业同一理由） |
| `〓` 分隔符删除 | 版式痕迹 |
| 全角数字/字母/空格转半角 | 仅转 ASCII 区，**不动中文标点**（第一版脚本误把全角逗号转成半角，导致逗号类标签丢失，已修复） |
| 多字标点词（如 `……`） | 分词器输出为一个词，需按"整词都是标点"处理，否则 `…` 漏进文本（已修复，标签中 `…` 1,587 例） |
| 混合词内标点（`abc，`、`’98`） | 撇号保留为文本；其余标点转为前一字的标签 |

### 1.3 训练与评测口径

- **模型**：`google-bert/bert-base-chinese`（经 hf-mirror 下载），`BertForTokenClassification`，11 类标签；字→token 对齐用 offset_mapping，每个字只在其**首个子词**上监督，CLS/SEP/pad 忽略。
- **训练**：2 epoch × batch 16 = 5,000 步（训练集取前 40,000 块），AdamW lr=3e-5，线性 warmup 10% 后线性衰减，梯度裁剪 1.0，类别加权（按训练集频率、截断 [0.1,10]，O 类减半）。
- **硬件口径**：课件假设 12G 显卡 batch 4–9、更好显卡 16–64（针对 400 字符窗口的推理场景）；本机是 **4GB 笔记本卡**，训练 batch 16（128 字符序列）峰值显存 2,824 MB（实测）。推理 batch 上限的实测与外推见 §3.4。
- **评测**：测试集逐字 macro-F1 + 各类别 P/R/F1（sklearn classification_report）；另给出"重建样例"（gold 与 pred 的全文对比）便于人工检查。

### 2.3 重建样例（gold vs pred）

（`results/samples.txt` 摘录；观察典型错误类型）

从重建样例看，错误集中在四类：

1. **引号漏标（最多）**：如"是'河西'家具超前消费"里的引号全部漏掉。原因：(a) 128 字符的块常常把引号对截断到不同块，模型看不到配对；(b) 引号位置本身歧义大（左引号前/右引号后的字与普通字无别）。
2. **逗号/句号混淆与漏插**："三高队同西班牙巴斯克省队对阵。" 被改成"对阵，"；"近年来不少国家还在……"漏掉了"近年来，"的逗号。这是断句任务最有实际影响的错误（改变句界）。
3. **冒号→逗号**："他又说：" 被改成"他又说，"——引语前的冒号信息在局部窗口内不足以确定。
4. **块边界截断伪影**："充满希望的21世纪！"在块边界被截成"……21世。"——这是数据切块（≤128 字符）造成的评估伪影，不是模型能力问题，实际长文解码（任务二）用 400 字符窗口且重叠融合，不受影响。

## 三、任务二：长文 batch 解码

### 3.1 问题重述

BERT 的 512 token 上限意味着数千字的古文必须滑窗。课件描述的朴素做法：窗口 400 字符 → 只保留前约 300 字符的结果 → 在预测的句号后断开作为新起点。它的低效有两个来源：(1) 每个窗口的前向是**串行**的——下一个窗口的起点依赖本窗口预测出的句号位置，无法并行；(2) 窗口利用率只有 75%（400 取 300），且句号后重启还丢弃一段。

### 3.2 方案设计：固定步长 + 重叠融合 + batch 并行

关键观察：**"句号后断开"是为了句子边界质量，而 batch 并行需要窗口之间互相独立**。二者可以解耦——用固定步长的窗口（几何形状与朴素方案相同：窗口 400、步长 300），让所有窗口的输入只依赖原文、彼此独立，从而可以装入同一 batch 并行前向；句子边界的质量改由**重叠区概率融合**保证（每个位置被 1–2 个窗口覆盖时取概率平均，再 argmax）。这样：

1. 串行依赖消除 → 全部窗口一次（或分批）前向，GPU 利用率从"1 个 400 字序列"提升到"batch 个 400 字序列"；
2. 重叠区（100 字符）的两份预测取平均，边界处的置信度比朴素方案"只信一次"更稳；
3. 词表头与编码器同 batch 计算，padding 可忽略（等长窗口）。

（实现见 `decode_long.py`：`run_method_A` 为朴素基线、`run_method_B` 为 batch 方案、`merge_overlap` 为概率融合。）

**速度**：B8 平均 1.34× 于 A（中位 1.13×，最高 2.70×），且耗时方差远小——A 在 doc 6 出现 1.29s 的抖动（串行逐窗，每个窗口的编码+前向+同步都进关键路径，任何一次抖动都直接叠加），B8 始终稳定在 0.47–0.48s。更关键的是结构差异：A 的窗口起点依赖上一窗口输出，**无法并行**；B 的窗口相互独立，10 个窗口只需 2 次前向。本机 GPU 计算量太小（400 字窗口一次前向仅几 ms），两方案的瓶颈都在 Python/框架调用开销而非 GPU，所以倍数有限；batch 扫描（§3.4）显示把窗口装进 batch 正是摊薄这一固定开销的手段。

**质量**：macro-F1 平均 A 0.232 vs B8 0.217（−0.015），weighted-F1 0.886 vs 0.878（−0.008），逐字一致性 0.900–0.952。A 的"句号后重启"让窗口起点总在句界，边界质量略好；B 用固定步长换并行性，代价是极小且方向不固定的宏平均差异（4 篇 A 好、3 篇 B 好、1 篇持平）。

**口径说明（为什么这里绝对 F1 只有 ~0.2 而 §2 是 0.56）**：我做了两个诊断脚本实测归因（`diag_long.py`、`diag_win.py`，结果 `results/diag_long.json`、`results/diag_window.json`）。

- **拼接伪影不是主因**：3000 字长文由测试集 128 字块拼接而成（块间来自不同文章，拼接点金标为 O 但模型按连续文本预测）。实测错误中仅 **13–14%** 距拼接点 ≤5 字，贡献有限。
- **窗口长度超出训练分布才是主因**：模型只在 ≤128 字块上训练（绝对位置嵌入只见过位置 0–127）。同文档用不同窗口解码（方法 B）：win 128→200→300→400，macro-F1 单调下降 **0.383→0.322→0.268→0.211**（doc0），weighted-F1 0.926→0.875。400 字窗口的大半位置在训练分布之外。
- 即便 128 字窗口，长文 macro（0.33）仍低于 §2 的 0.561：重叠滑窗把原块切在不同位置，窗口边缘位置上下文不完整，且拼接点伪影仍在；O 类 F1 始终 ~0.94（weighted ~0.88–0.93），说明"该不该加标点"的主体判断没有崩塌，塌的是具体标点类的判别。

**这条归因是任务二最有价值的工程结论**：课件默认"窗口 400/取 300"的几何形状只在模型见过 400 字序列时成立；滑窗长度是超参数，必须与训练序列长度匹配（或训练时做长度混合/位置插值）。我的 batch 解码方案（§3.2）把窗口几何与并行策略解耦，因此换窗口长度不需要改方案——上面的 128 字窗口对照用的就是同一个 `run_method_B`。

### 3.4 batch 上限扫描与课件规格对照

（表：batch 1/2/4/8/16/32 的耗时、吞吐、显存峰值——方法 B，第 0 篇文档）

| batch | 耗时(s) | 吞吐(字/s) | 峰值显存(MB) |
|---|---|---|---|
| 1 | 0.561 | 5,346 | 696 |
| 2 | 0.484 | 6,202 | 696 |
| 4 | 0.456 | 6,586 | 696 |
| 8 | 0.430 | 6,970 | 696 |
| 16 | 0.412 | 7,289 | 696 |
| 32 | 0.395 | **7,601** | 696 |

batch 1→32 吞吐提升 **42%**，峰值显存不随 batch 增长——400 字窗口的中间激活很小，显存大头是模型权重本身（fp32 约 400MB）。

**与课件规格的对照**：课件说"12G 显卡 batch 可开 4–9、更好显卡可开 16–64"。我们的实测是 4GB 笔记本卡就能开到 batch 32 无 OOM，说明课件的 4–9 是保守估计（或针对 fp32 全模型 + 512 token 长序列 + 未做流水的旧实现）。换算上：batch 解码的显存增量主要在中间激活，与 batch 近似线性；按激活占显存的比例外推，12G 卡（权重 400MB 后剩约 11GB 给激活）开 16–64 毫无压力，课件上限 64 对应的就是"更好显卡"档。真正随 batch 变化的不是显存而是**吞吐收益的边际递减**：batch 1→2 +16%、2→4 +6%、4→8 +6%，到 16→32 只剩 +4%——瓶颈从调用开销转向 GPU 计算，这正是课件要求"设计 batch 解码方案"的工程要点：**用 batch 摊薄固定开销，而不是无脑加大 batch**。

## 四、古文句读定性演示

用现代文训练的模型给无标点古文（《岳阳楼记》《师说》《爱莲说》节选）做句读（`results/gushi_demo.txt`）。**仅为定性展示**：训练域是 1998 年新闻，古文是跨域应用，不做定量声明。观察（逐字对照人工标点）：

1. **大部分句界和逗号落在合理位置**，且常落在文言虚词后（"……也。""……乎？""……矣。""……焉。"）——现代文的"语气词+句尾标点"模式迁移到了文言。
2. **典型错误一：四字格/固定结构被切开**。"迁客。骚人""予观。夫""在洞庭，一湖"——模型把现代文的词界直觉套在文言词组上。
3. **典型错误二：排比四字句内部漏逗号**。"山岳潜形商旅不行樯倾楫摧薄暮冥冥虎啸猿啼。"整段未断，与任务一的错误类型一致（局部窗口内连续短句边界信息不足）。
4. **典型错误三：叹号/问号选择**。"此乐何极！"被标成"此乐，何极……？"、"噫！"漏叹号——叹号在训练语料中本来就只有 50 例支持（§2.2），是最弱类之一。

结论：断句的主干能力（在哪里断）对跨域古文有意外好的迁移，但"断在哪、用什么标点"的细节仍受训练域限制。这正是任务二"滑窗解码"要服务的真实场景——古文段落数千字，只能滑窗，而滑窗方案的吞吐与质量权衡已在 §3 实测。

## 五、局限与诚实声明

1. **算力**：本机 4GB 显存，训练 batch 16（128 字符）与课件"12G batch 4–9"的推理规格不是同一件事；batch 解码的并行收益在 4GB 卡上已可见，12G 上的数值是线性外推。
2. **数据划分**：随机按块划分（非按文章），测试块与训练块可能同源——影响 F1 的"绝对值"，但不影响任务一/任务二的流程与相对结论（两种解码方案在同一测试集上比较）。
3. **窗口长度与训练分布不匹配**：模型在 ≤128 字块上训练，任务二按课件规格用 400 字窗口解码，位置嵌入超出训练分布，长文绝对 F1 因此偏低（§3.3 已实测归因，128 字窗口 macro 0.33 vs 400 字 0.20）。两方案 A/B 在同一窗口长度下比较，相对结论不受影响；正确修法是长度混合训练或限制滑窗长度。
4. **引号类标签**："" 两类合并了直引号/单引号变体，重建时统一输出 ""；语料中引号不平衡（" 39,620 vs " 32,778）来自跨块引号对与撇号，对序列标注无影响。
5. **O 类主导**（92.6%）：macro-F1 对稀有类敏感，报告时同时给出各类别 support。
6. 训练集只用了前 40,000 块（全部 96,270 块的 41.5%），2 epoch——若追求更高绝对分，可全量训练更多 epoch；本作业目标是完整跑通流程并回答问题，不是刷分。
