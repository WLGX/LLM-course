### 1.2 检索观察

1. **PyTorch 类仓库整体是"教学/复现"型**：453 个仓库里没有一个被社区当生产工具用；生产环境的事实标准是 gensim（Python）与原版 C。老师"GitHub 上很多是玩具实现"的判断与检索结果一致。
2. **维护状态分层明显**：原版 C 系（tmikolov/dav/mccormick 注释版）多年未动但长期有效；PyTorch 系平均停在 2019–2022；gensim 与 numpy-ml 是少数持续维护的。
3. **NumPy 系几乎全是玩具**：绝大多数无负采样、无降采样；numpy-ml 是例外（有 SGNS + numba 加速），但 numpy-ml 是"机器学习算法库"，word2vec 只是其中一个模块。

## 二、三个实现的实际运行对比

### 2.1 语料与参数对齐

- 语料：与 4.2 完全相同的清洗语料 `4_2/data/rmrb_9801_06.seg.txt`（123,761 句 / 6,134,949 词次，北大分词，1998-01~06 人民日报）。

### 2.2 同口径评测（近邻 / 相似度 / 类比 / OOV）

评测脚本 `scripts/eval_vectors.py`（探针与 4.2 完全一致），结果 `results/impl_compare_eval.json`：

| 探针 | gensim SG d100 | 原版 C SG d100 | PyTorch SGNS |
|---|---|---|---|
| 中国 近邻 top5 | 苏里南/西班牙/意大利/我国/罗马尼亚 | 我国/苏里南/所在国/德意志/马克斯·魏勒 | 奠基人/橄榄球/创始人/基督教/藏学 |
| 经济 近邻 top5 | 国民经济/经济基础/OECD/国有化/稳步前进 | 国民经济/高级化/对外贸易/房地产业/产业 | 国民经济/命脉/开放型/发展/加速 |
| 类比 中国:北京::美国:? | 华盛顿/渥太华/洛杉矶 | 华盛顿/洛杉矶/莫斯科 | 雅加达/开罗/20日 |
| doesn't_match[北京上海天津足球] | 足球 ✓ | 足球 ✓ | 足球 ✓ |
| OOV 深度学习/神经网络/微信/智能手机 | 全部 KeyError | 全部 KeyError | 全部 KeyError |

初步判断：gensim 与原版 C 学出的是**同一个语义空间**——"中国"的近邻都以国名/地区为主，"经济"近邻都落在经济词域，类比都给出真实首都（华盛顿居首），doesn't_match 都正确。两个实现的随机种子、线程调度、学习率衰减细节都不同，top5 的排序和边缘成员有差异属预期；**质量差异远小于实现栈差异**。

PyTorch 实现则明显弱一档："中国"的近邻是 奠基人/橄榄球/基督教 这类"人物+名物"混合（不再是国名域），类比给出 雅加达/开罗（两个真首都，但混入了"20日"这样的噪声词）。原因不在 PyTorch 本身，而在该实现缺的算法细节（见 2.3.2）：**没做降采样**（高频词淹没梯度）、**Adam 用默认 lr=1e-3 且无衰减**（C/gensim 是 SGD/ASGD，lr 从 0.025 线性衰减到 1e-5）、**词表用 rank 截断到 50000**（比 min_count=5 的 42,702 多出约 7 千个只出现两三次的噪声词）、窗口边缘用 `<UNK>` 填充。这些差异叠加，同样 5 轮训练下质量就有可见差距——这正是"算法细节完整度比框架选择更重要"的直接证据。

### 2.3 跑通过程中发现的问题（这是"跑过才有"的部分）

1. **原版 C（dav fork）**：
   - Makefile 的**默认目标是 `clean`**——直接 `make` 会清掉示例数据并退出，必须 `make build`（进入 src/ 编译）。第一次编译就踩了这个坑。
   - 输出文件**不自动加 `.bin` 后缀**（原版 word2vec.c 会拼 `.bin`，dav fork 按 `-output` 原样写），gensim 加载时按 binary 格式读 `results/c_sg100` 即可。
   - 自动在每行句末加 `</s>` 句尾符，词表 42,703 = 42,702 + 1。
   - 训练日志证实论文的超参数全部对应到命令行：`Alpha` 从 0.025 线性衰减到 0.00001、`Words/thread/sec` 实时打印（这是"观察训练过程"的直接材料）。

2. **pytorch-sgns**：
   - **Windows + torch 2.9 下第一批训练直接崩**：`torch.LongTensor(int32 ndarray)` 报 `TypeError: expected TensorOptions(dtype=__int64) ... got dtype=int`。原因链：Windows 的 numpy 默认 int32（Linux 为 int64）→ DataLoader 把 np 数组拼成 int32 ndarray → 新版 torch 不再隐式转换。作者在 Linux + 旧 torch 环境下不会遇到。**修复一行**（`LT(data)` → `LT(np.asarray(data, dtype=np.int64))`），原文件保留为 `model.py.orig`，崩溃日志 `results/torch_train_fail_log.txt`。
   - **降采样实现了但没接上**：`train.py` 里 `ws = 1 - np.sqrt(ss_t / wf)` 算好了 subsample 概率，但 `PermutedSubsampledCorpus` 没传 `ws`，实际训练没做降采样。
   - **负采样分布默认不对**：不加 `--weights` 时从均匀分布抽负样本（论文是 3/4 幂频次分布），必须显式加 `--weights`。
   - `preprocess.py` 不会创建 `--data_dir` 目录（train.py 反而会创建 save_dir）；窗口边缘用 `<UNK>` 填充到固定 10 个上下文词（gensim/原版 C 是截断）。
   - 优化器用 Adam（原版 C/gensim 用 SGD/ASGD）且学习率无衰减——这是教学实现与生产实现的典型差别之一。
   - 训练速度：同样的语料与轮数，**26.5 分钟 vs 原版 C 60.6 秒**（约 26 倍差距）；评测质量也弱一档（见 2.2 判断），差距来源即上述缺失的细节。

3. **DerekChia/word2vec_numpy（玩具实现的三重问题）**：
   - **连自带 demo 都跑不起来**：`np.array(training_data)` 在 numpy≥1.24 下因窗口边缘上下文数不等长（ragged array）直接 `ValueError`（失败日志 `results/numpy_demo_output.txt`）。同样一行修复（`dtype=object`）后 demo 跑通（补丁版 `scripts/numpy_demo_patched.py`，loss 50 轮从 ~64 降到 ~57）。
   - 权重矩阵 `getW1`/`getW2` **硬编码为 9×10/10×9**——词表必须恰好 9 个词，换任何真实语料都会形状不匹配。这就是"玩具"的本质：为 demo 调好的常量。
   - 算法层面：完整 softmax（每步 O(V)）、每个训练样本物化成 one-hot（内存 O(V)）、无负采样/降采样/min_count。按 12 万句人民日报估算：词表 ~13 万时一个样本的 one-hot 就 ~0.5MB，整个语料物化需要 ~3TB 内存——**玩具实现无法搬到真实语料，不只是"慢"，而是量级上不可行**。

4. **跨实现的通用观察**：速度分层是 C/Cython（约 1 分钟）≫ 纯 Python 批处理 PyTorch（26.5 分钟，约 26 倍）≫ 纯 Python 逐样本循环（无法完成）。**评测质量的分层方向一致但幅度小得多**：C/gensim 都在类比探针上给出真实首都，PyTorch 实现弱一档但仍可识别出 雅加达/开罗 这类首都。这说明 word2vec 的"算法细节"（3/4 幂噪声分布、降采样、min_count、优化器与学习率衰减）比"用什么框架写"更决定成败，而这些细节恰恰是玩具实现最容易丢的。

## 三、教程与博客阅读笔记

除经典论文（4.2 报告 §5 已对照）外，本次阅读了 Rong Xin《word2vec Parameter Learning Explained》（arXiv:1411.2738）、Chris McCormick 的 skip-gram 两篇教程、Jay Alammar《The Illustrated Word2Vec》，完整笔记在 `notes/教程博客笔记.md`。要点：

1. Rong 的论文给出完整的梯度推导，其中 NS 的**统一更新式** `v'(new) = v'(old) − η(σ(v'ᵀh) − t_j)h`（正样本 t_j=1、负样本 t_j=0）是看懂 gensim `syn1neg` 与原版 C `neu1e` 更新代码的钥匙；HS 的路径乘积式解释了"每个内部节点一个向量"的存储布局。
2. McCormick 的工程视角补齐了"输出矩阵才是代价所在""负样本数小数据 5–20 / 大数据 2–5""min_count 去噪词"这些论文一笔带过的实操判断。
3. Alammar 的图解给出直觉：负采样 = 把"V 分类"换成"neighbor / not-neighbor 二分类"，以及 king−man+woman≈queen 的线性类比画面（对应本报告的类比探针）。

三份资料的互补关系：论文讲"为什么"、Rong 讲"梯度怎么算"、McCormick 讲"工程怎么落地"、Alammar 讲"直觉怎么建"——正好覆盖"论文 → 代码 → 编程技巧"三层。

## 四、结论与自查

**结论**：
1. 同一算法（SGNS）在三个实现栈上训练同样的语料：原版 C/gensim 开箱即跑且质量相当（类比探针都给出真实首都）；pytorch-sgns 需要一行兼容补丁才能跑，训练慢约 26 倍、质量弱一档（仍能识别部分首都）；numpy 玩具连 demo 都要补丁，且硬编码形状决定了它无法上真实语料。
2. "实现对比"的本质是**对比算法细节的完整度**：3/4 幂噪声分布、降采样、min_count、优化器与学习率衰减，这些细节在论文里各占一行，在代码里各差一个分支，在评测结果里各值几个百分点的质量——4.2 的消融（min_count、维度）和本报告的代码对照合起来，把这个链条的两端接上了。
3. 选型结论（与 4.2 呼应）：生产/实验首选 gensim（流式、可继续训练、算法细节齐全）；需要复现原版数字时用原版 C；PyTorch 实现适合教学阅读，直接用需先补降采样与学习率调度；numpy 实现只适合理解原理。

**三档自查**：基础（GitHub 检索、跑通代码、记录参数与结果）✓；进阶（读论文并对比实现——4.2 §5 + 本报告 2.3 代码级对照）✓；高级（理解周边代码与超参数——C 的 unigram table/学习率衰减、pytorch-sgns 的 Adam/批负采样、各实现初始化差异）✓。
